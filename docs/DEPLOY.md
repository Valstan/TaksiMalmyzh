# Выкатка на прод

Процедура и её обоснование. **Конкретные адреса, порты, пути и имена — не здесь**:
репозиторий публичен, и такие детали в него не пишутся (`AGENTS.md`, «Публичный
репозиторий — recon-поверхность»). Они лежат в карточке проекта на стороне brain и в
секретах GitHub.

---

## Главное решение: собирать в CI, на сервер везти готовое

Прод-бокс маленький. Собрать на нём Next-приложение **нельзя**: процесс ловит OOM, а swap
на контейнерном VPS не включается — `swapon` отвечает «Operation not permitted». Это
чужая уже оплаченная ошибка (G20), повторять её незачем.

Поэтому:

```
CI собирает  →  пакует release/  →  везёт на сервер  →  симлинк  →  рестарт  →  смоук
```

Рантайм в пакете — **24,5 МиБ** (замер 2026-08-29), из них 2,4 МиБ карта. Такой пакет
бокс тянет свободно; тяжёлая только сборка, и она уезжает в CI.

## Что собирается

```bash
npm ci
npm run build      # output: "standalone"
npm run package    # release/ — рантайм + .next/static + public + data
```

`npm run package` существует потому, что `output: "standalone"` кладёт в
`.next/standalone` только рантайм: **статику сборки и `public/` Next не копирует**. Без
них приложение поднимется и отдаст страницу без стилей и без карты. Скрипт докладывает их
и проверяет, что в пакете есть `server.js`, `.next/static`, вырезка карты и адресный
справочник, — иначе падает.

Адресный справочник читается с диска в рантайме, поэтому он явно включён в трассировку
(`outputFileTracingIncludes` в `next.config.mjs`). Без этого поиск на проде отвечал бы
«такого адреса нет» на любой запрос — и заметили бы это не сразу.

## Раскладка на сервере

Релизы кладутся по одному в каталог, `current` — симлинк на активный:

```
<каталог приложения>/
  releases/2026-08-29-<sha>/   ← распакованный пакет
  current -> releases/...      ← симлинк, его переключение и есть выкатка
  shared/.env                  ← секреты, вне репозитория и вне пакета
```

Откат — переключение симлинка на предыдущий релиз и рестарт. Старые релизы чистятся,
оставляя последние несколько.

В `shared/.env` живут и выключатели функций, не только секреты: `TRACK_RECORDING=on`
(запись поездок) и `OIDC_CLIENT_ID=pozvoni` (вход через единый вход экосистемы,
[`AUTH_ESA.md`](AUTH_ESA.md)). Без переменной соответствующих роутов не существует —
приложение отвечает 404, а не «закрыто». Состав переменных — `.env.example`.

Служба запускается как `node current/server.js` под systemd, слушает **локальный** порт.
Наружу её публикует nginx бокса.

## HTTPS: сертификат ставится в панели, а не certbot'ом

Выделенного IP у бокса нет, внешние 80 и 443 терминирует прокси хостера и форвардит оба
на внутренний `:80` с заголовком `X-Forwarded-Proto`. Отсюда два следствия (G150):

- **certbot бесполезен** — свой `:443` снаружи недостижим. Сертификат Let's Encrypt
  ставится через панель хостера, продлевается там же.
- **Редирект на http→https делается по `$http_x_forwarded_proto`**, а не по `$scheme`:
  по `$scheme` получается петля, потому что внутрь всегда приходит http.

У свежесозданного поддомена установка сертификата из панели может не пройти с первого
раза: до появления серта прокси крутит петлю редиректов, и валидатор в ней умирает
(G153).

## Порядок первой выкатки

**Шаг 1 — разово на боксе, под `sudo`.** Скрипт заводит каталоги, кладёт публичный
деплой-ключ, ставит systemd-юнит и секцию nginx:

```bash
git clone --depth 1 https://github.com/Valstan/TaksiMalmyzh.git /tmp/taksi-bootstrap
sudo bash /tmp/taksi-bootstrap/deploy/bootstrap-box.sh \
     --user <пользователь> --dir <каталог> --port <порт> \
     --service <имя службы> --domain "<домен> [<домен> ...]" --key "<публичный ключ>" \
     [--closed <файл паролей basic-auth>]
```

Значения в скрипт приходят аргументами и в репозиторий не попадают. `--closed` включает
basic-auth: пока приложение не готово к этапу B, посторонних пускать не нужно.

`--domain` принимает **несколько доменов через пробел**: у продукта матрёшка доменов
([`DOMAINS.md`](DOMAINS.md)), и все они обслуживаются одной секцией nginx и одним
приложением — какое лицо показать, оно решает по заголовку `Host`. Добавить домен позже =
запустить скрипт ещё раз с **полным** списком: секция перезаписывается целиком, ключ и
systemd-юнит повтор переживают.

**Шаг 2 — секреты GitHub.** Заводить именно **секретами**, не `vars`: значения `vars`
печатаются в лог прогона, а логи публичного репозитория публичны.

| Секрет | Что это |
|---|---|
| `DEPLOY_SSH_KEY` | приватный деплой-ключ (пара генерируется отдельно от ключей владельца) |
| `DEPLOY_KNOWN_HOSTS` | ключи хоста — чтобы выкатка не принимала их вслепую |
| `DEPLOY_TARGET` | `пользователь@хост` |
| `DEPLOY_SSH_PORT` | порт SSH |
| `DEPLOY_APP_DIR` | каталог приложения |
| `DEPLOY_SERVICE` | имя systemd-службы |
| `DEPLOY_SMOKE_URL` | адреса для смоука после выкатки — **через пробел, по одному на живой домен** |

**Шаг 3 — домен.** DNS на бокс, затем сертификат **из панели хостера** (не certbot).
Каждому домену матрёшки — свой сертификат; полный чек-лист заведения нового домена, включая
то, что легко забыть (запись в реестре и адрес в смоуке), — [`DOMAINS.md`](DOMAINS.md) §7.

**Шаг 4 — выкатка.** Запустить workflow `deploy` вручную. После неё автоматически идёт
**смоук**: страница отдаёт `200`, `/api/search?q=Прибрежная` возвращает улицу,
`/map/malmyzh.pmtiles` отдаёт `206` на Range-запрос, воркер MapLibre отдаётся **с JS-типом**,
`/nomera` отдаёт `200` (значит, миграции применились и база жива). Каждая проверка
соответствует поломке, которая уже случалась при постройке.

Проверка типа воркера появилась 2026-08-30 после того, как карта сломалась у пользователей
из-за одного лишь `Content-Type`: nginx не знал расширения `.mjs`. Смоук тогда был зелёным —
он спрашивал «файл отдаётся?», а надо было «чем отдаётся?».

⚠️ **Чего смоук не проверяет и проверить не может: что карта нарисовалась.** Рисование — это
WebGL в браузере. Проверять глазами и только на **выведенной вперёд** вкладке: в скрытой не
срабатывает `requestAnimationFrame`, и MapLibre остаётся с незагруженным стилем — серый
прямоугольник без единой ошибки, неотличимый от настоящей поломки.

Смоук идёт сначала по локальному порту, затем **по каждому публичному адресу из
`DEPLOY_SMOKE_URL`** плюс проверка сертификата. Домен, не попавший в этот секрет, не
проверяется вообще: его поломку найдёт пользователь, а не прогон.

## ⚠️ Миграции применяются на старте — и могут повесить старт вопросом

`payload.config.ts` содержит `prodMigrations`: непринятые миграции применяются при запуске
службы. Влить миграцию и выкатить схему на прод — **одно действие**, не два.

Отсюда правило, нарушение которого стоит простоя: **против прод-базы никогда не запускать
`next dev`.** Дев-режим оставляет в `payload_migrations` строку `dev`, и тогда Payload на
старте не применяет миграции молча, а печатает «data loss will occur. Would you like to
proceed? (y/N)» и **ждёт ввода**. Под systemd вводить некому — служба висит, сайт не
поднимается. Проверено на релизном пакете (`docs/TRIP_SCHEMA.md` §3).

Проверить перед выкаткой миграции: в `payload_migrations` прод-базы строки `dev` быть не
должно.

## ⚠️ Что выкатка меняет юридически

Пока стенд закрыт, единственный субъект персональных данных — владелец. **В момент, когда
приложение становится доступно из интернета, в логах веб-сервера появляются IP
посторонних людей — это уже чужие персональные данные и этап B**
([`GO_LIVE_CHECKLIST.md`](GO_LIVE_CHECKLIST.md)).

Это не запрет выкатывать, а факт, который стоит принимать осознанно. Дешёвый способ
выкатить и не пересечь границу — закрыть стенд basic-auth или по IP и не логировать
адреса посетителей, пока приложение не готово к этапу B.

## Проба прода: то, что ломается между выкатками

Смоук отвечает на «релиз поднялся?» и идёт только при выкатке. Между выкатками прод не
проверял никто, а самые дорогие поломки устроены именно так — тихо и постепенно. Отсюда
`probe-prod` (`.github/workflows/probe-prod.yml` + `deploy/remote-probe.sh`): раз в сутки и
по кнопке, только чтение, всё — с бокса.

| Что смотрит | Почему это класс поломки, а не мелочь |
|---|---|
| колонки `payload_locked_documents_rels` против списка коллекций | коллекция без своей колонки роняет админку целиком, гейты этого не видят по построению (G231) |
| свежесть и отказы в `track.maintenance_run` | регламент перестал ходить — сроки хранения тихо не исполняются (M0.A §3.4) |
| запас партиций приёма точек | без партиции вставка падает у человека, который уже едет |
| возраст самой старой партиции | сырьё, пережившее свой срок, — это данные, которые обещали стереть и не стёрли (M0.A §3.4) |
| ответ приложения по локальному порту | служба лежит — между выкатками этого не видит никто |
| строка `dev` в `payload_migrations` | следующая выкатка с миграцией повесит старт вопросом (см. выше) |
| выход из ЕСА | наш роут → `end_session` → возврат к нам |
| срок сертификатов | продление — чужой автомат в панели хостера, его отказ виден только истёкшим сертификатом |

**Красный прогон пробы — это и есть алертинг проекта**: письмо о нём присылает GitHub.
Поэтому в пробе нет «предупреждений», которые никого не будят: проверка либо падает, либо
молчит. Отсюда же требование к порогам: они должны падать по делу. Проверка, вечно красная
из-за чужой сети, научит игнорировать красный цвет — по этой причине недоступность ЕСА
поломкой не считается, а пишется строкой.

Пороги совпадают с приложением намеренно (25 часов, 3 суток запаса партиций): проба и
планировщик должны считать поломкой одно и то же, иначе один будет молчать там, где другой
кричит.

## Что эта процедура не покрывает

- **Базу данных на проде.** На боксе PostgreSQL уже стоит — проекту нужна своя база и
  роль, а не свой сервер. Понадобится в спринте 3, когда появится схема поездок.
- **Сертификат.** Ставится в панели хостера руками, автоматизировать нечего.
- **DNS.** Тоже разовое действие владельца.
