# Вход через единый вход экосистемы (ЕСА, `вход.вмалмыже.рф`)

Построено 2026-09-02 по просьбе владельца «вход через ВК» (2026-08-29), уточнённой
02.09: **для посетителей, аккаунт создаётся сам при первом входе, кнопка и имя — в шапке
сайта.** Прямой интеграции с ВК нет: единый вход экосистемы делает ЕСА, а ВК для неё — один
из способов войти. Сайту это невидимо и таким останется: ЕСА отдаёт только `sub`, `name` и
по scope `email` (решение владельца D-063). Пользователь ПОЗВОНИ = `sub`.

## Кто и что получает

| Роль | Как появляется | Что может |
|---|---|---|
| `user` — посетитель | сам, первым входом через ЕСА | видеть своё имя в шапке, выйти; в админку не попадает, список пользователей не видит, роль поднять не может |
| `superadmin` — персонал | заводит владелец в админке, входит паролем; **привязывает** ЕСА из живой сессии | админка, модерация, запись поездок этапа A |

**Забор M0.A §10 цел** ([`PRIVACY_GEODATA_DESIGN.md`](PRIVACY_GEODATA_DESIGN.md)): аккаунт
посетителя не соединяется с трассами. Гейт записи поездок (`lib/track-gate.ts`) пускает
только `superadmin`; открыть запись посетителям — этап B (чужие персональные данные) и
отдельное решение владельца. Справочник по-прежнему анонимен: смотреть номера и звонить
можно без входа.

Персональные данные посетителя в нашей базе — имя из ЕСА и устойчивый `sub`. Почту не
запрашиваем. Логин посетителя — хэш `sub` (идентификатор чужой системы в списке
пользователей ни к чему), пароль случайный и никому не известен: единственный вход для
такого аккаунта — ЕСА.

## Реквизиты клиента (прод, заведён 2026-09-01)

| Поле | Значение |
|---|---|
| issuer | `https://вход.вмалмыже.рф` (`https://xn--b1ae3a1a.xn--80adkdyec4j.xn--p1ai`) |
| `client_id` | `pozvoni` |
| тип | **public**, Authorization Code + PKCE S256, `token_endpoint_auth_method=none` |
| `redirect_uri` | ровно один: `https://позвони.вмалмыже.рф/api/auth/oidc/callback` (в punycode — так строит `lib/oidc.ts` из `lib/sites.ts`) |
| scopes | `openid profile` |
| discovery | `/.well-known/openid-configuration`; JWKS — по discovery (`/.well-known/jwks.json`), RS256 |
| logout | у ЕСА нет ни `end_session_endpoint`, ни back-channel; наш выход — только своя сессия |

Секрета **не существует** — хранить и ротировать нечего. Всё, что нужно на боксе, —
`OIDC_CLIENT_ID=pozvoni` в env приложения; это выключатель, а не секрет.

## Как устроено

- `lib/oidc.ts` — конфигурация, discovery с кэшем, PKCE, обмен кода, проверка ID-токена
  (подпись по JWKS, issuer, audience, nonce). Личность берётся из проверенного
  ID-токена, не из `/userinfo`.
- `lib/oidc-flow.ts` — состояние одного прохода (`state`, `nonce`, `verifier`, режим,
  `next`) в httpOnly-куке `oidc-flow` с путём `/api/auth/oidc` и сроком 10 минут;
  одноразовая. `next` — только относительный путь (не открытый редирект).
- `app/(app)/api/auth/oidc/start` — начало. Гость → режим `login`; вошедший (обычная
  сессия Payload) → режим `link`.
- `app/(app)/api/auth/oidc/callback` — возврат. `link`: привязывает `sub` к учётке живой
  сессии. `login`: находит пользователя по `sub` или **создаёт посетителя**, обновляет имя,
  выдаёт сессию, возвращает на `next` (иначе персонал → `/admin`, посетитель → `/`).
- `app/(app)/api/auth/logout` — выход, только POST: снимает куку и отзывает сессию в
  `users.sessions`.
- `lib/oidc-session.ts` — выдаёт ту же сессию Payload, что и парольный login
  (`sessions` + JWT + кука `payload-token`). `lib/session.ts` — текущий пользователь для
  серверных компонентов.
- `collections/Users.ts` — роли `superadmin`/`user`, поля `name`, `oidcSub` (уникальное,
  readOnly, через API не обновляется), `access.admin` только персоналу, чтение посетителю —
  только себя. Миграции `20260902_120000_oidc_sub`, `20260902_180000_visitor_role_name`.
- `components/SiteHeader.tsx` — «Войти» / «👤 имя · выйти» на всех лицах матрёшки.
- Админка: ссылка под формой логина (`beforeLogin`) и карточка привязки на главной
  (`afterDashboard`). Всё молчит, пока `OIDC_CLIENT_ID` не задан.

## Редиректы и куки — от реестра доменов, не от запроса

За nginx приложение видит себя как `localhost:<порт>`, поэтому `request.url` для
редиректов непригоден: первый живой вход 2026-09-02 вернул владельца на `localhost`.
`publicOrigin()` в `lib/oidc.ts` в проде берёт `https://` + корневой хост из `lib/sites.ts`
и ставит кукам `Secure`; локально — адрес запроса.

Если персонал уже входил этим аккаунтом ЕСА как посетитель, привязка из админки переносит
`sub` на сотрудника и удаляет пустую посетительскую учётку — руками ничего удалять не надо.

## Почему вход только на корневом домене

Redirect URI один, и он на `позвони.вмалмыже.рф`: иначе каждый новый поддомен матрёшки
становился бы заявкой на чужой стороне. С поддомена кнопка «Войти» ведёт на корень, и
после входа человек остаётся там. Кука сессии Payload хостовая **намеренно**: кука на всю
зону `.вмалмыже.рф` уезжала бы соседним проектам той же зоны. Если владелец захочет
сессию и на `такси.` — это отдельное решение с этим компромиссом.

## Что проверить на проде после первой выкатки с `OIDC_CLIENT_ID`

1. `GET /api/auth/oidc/start` → `302` на `…/oidc/authorize?client_id=pozvoni&…code_challenge_method=S256`.
2. Посетитель: «Войти» в шапке → ЕСА (пароль или ВК) → возврат на сайт, вверху имя;
   «выйти» → имя пропало; `/admin` под посетителем — не пускает.
3. Персонал: войти паролем → карточка «Не привязан» → «Привязать» → ЕСА → возврат в
   `/admin`, карточка «Привязан». Выйти → под формой логина «Войти через единый вход» →
   `/admin` без пароля.

Проверено локально 2026-09-02 с настоящей сессией Payload (скриптом): имя в шапке, отказ
`/admin`, список пользователей посетителю не виден, самоповышение роли через REST отбито,
выход отзывает токен. Полный круг с ЕСА — только на проде.

Смоук без браузера — четыре `curl` у Сарафана (`docs/ops/esa-smoke-without-browser.md`
в их репозитории, только чтение). Для него нужен тестовый аккаунт ЕСА: саморег с
инвайт-кодом из vault владельца. Для публичного клиента шаг 3 их смоука идёт без `-u`,
с `client_id` и `code_verifier` в теле.

Прогнан 2026-09-03 без аккаунта (письмо `to-brain/2026-09-03-esa-smoke-run-…`): discovery,
JWKS и регистрация клиента подтверждены; `redirect_uri` байт-в-байт — нет, его закроет
только живой круг. ⚠️ Проверка «`authorize` без сессии → 302» из памятки Сарафана
провалиться не может: гейт по сессии срабатывает раньше валидации клиента, и пустой
`client_id` даёт тот же ответ. Регистрацию подтверждает `POST /oidc/token` с заведомо
неверным кодом: `invalid_grant` — клиент заведён, `invalid_client` — нет.

## Данные посетителя: уведомление и срок

Аккаунт посетителя — чужие персональные данные (имя из ЕСА и устойчивый `sub`), поэтому
этап A по бумагам открыт входом, а не поездками: разбор brain 2026-09-02, принят без
возражений. Решение владельца 2026-09-03 — **уведомление и ретеншн 12 месяцев**.

- **Уведомление** — `app/(app)/dannye/page.tsx`, ссылка «Ваши данные» в шапке рядом со
  входом (точка, где данные и появляются). Пишет только то, что уже устроено: два поля от
  ЕСА, почту не запрашиваем, согласие живёт у ЕСА, срок 12 месяцев, и чего аккаунт не знает
  (трассы на псевдониме установки, оценки на псевдониме устройства, вызов живёт 30 суток).
  Число месяцев на странице — из `ACCOUNT_RETENTION_MONTHS`, не переписанное руками.
- **Отметка входа** — `users.lastLoginAt`, миграция `20260903_200000_last_login`. Двигает её
  только выдача сессии (`lib/oidc-session.ts`), и ставится она **вне** ветки `useSessions`:
  иначе выключение сессий тихо сделало бы все аккаунты вечными. По `updatedAt` считать
  нельзя — его двигает любая правка строки, включая нашу же чистку сессий.
- **Ретеншн** — `lib/account-retention.ts`, в часовом регламенте
  (`lib/track-scheduler.ts`), с записью в `track.erasure_log` (без имени и `sub`: журнал
  доказывает исполнение срока, а не хранит то, срок чего вышел).

Четыре исключения из удаления, и они важнее самого удаления:

| Кого не трогаем | Почему |
|---|---|
| `superadmin` | персонал входит паролем и может не заходить месяцами; удалить владельца по сроку — потерять админку |
| владельца карточки бизнеса | `entries.owner_id` объявлен `ON DELETE SET NULL`: удаление не упало бы с ошибкой, а **тихо** сняло бы владельца с карточки вместе с кабинетом и работниками |
| заявителя с неподтверждённой заявкой | заявку подтверждает персонал звонком, между подачей и звонком проходит время; удалить заявителя — оборвать процедуру молча |
| учётку без `oidcSub` | отметку двигает только вход через ЕСА; парольная учётка выглядела бы мёртвой вечно, а удалять по сроку, которого мы для неё не измеряем, нельзя |

**У исключения по заявке есть дно — 30 дней** (`CLAIM_GRACE_DAYS`, решение владельца
2026-09-03). Заявка, до которой персонал не дошёл за срок, гаснет в статус **3 «истекла без
ответа»** (`expireStaleClaims` в часовом регламенте) и перестаёт защищать аккаунт. Возраст
проверяется и в самом предикате ретеншна, а не только через статус: между часовыми прогонами
заявка ещё числится ждущей, и без этого условия защита была бы вечной. Исключение из срока не
может само быть бессрочным, иначе оно отменяет срок.

Тройка заведена отдельным статусом, а не сведена к двойке: «отклонена» означает решение
человека, и автомат, ставящий её по таймеру, задним числом припишет персоналу отказ, которого
тот не выносил. Разница видна и заявителю — отклонённую заявку повторять бессмысленно,
истёкшую можно подать заново (`createClaim` переоткрывает только статус 3).

**Порядок операций выбран осознанно:** перепроверка (`FOR UPDATE SKIP LOCKED`) → удаление →
уборка ссылок и запись в журнал. Обратный порядок выглядит безопаснее, но при отказе
удаления оставляет **живого** человека без его заявок и со строкой в журнале, утверждающей,
что его стёрли. Цена выбранного — окно между удалением и уборкой; его закрывает
`sweepOrphanUserRefs`.

За удалённым убираются ссылки, у которых внешнего ключа на `users` нет вовсе:
`market.claim` (его заявки — удаляются), `market.request.customer_user_id` и
`track.share.viewer_user_id` (обнуляются: вызов принадлежит бизнесу, ссылка — тому, кто
писал поездку). Уборка вынесена в `detachUserReferences`, а `sweepOrphanUserRefs` в том же
регламенте подметает висячие ссылки **независимо от того, кто удалил человека**: путей
удаления в проекте три — регламент, админка и слияние посетительской оболочки при привязке
ЕСА. Инвариант, который держится только одним путём, не инвариант.

⚠️ **Слияние оболочки** (`app/(app)/api/auth/oidc/callback`) до 2026-09-03 удаляло
посетительскую учётку как «пустую оболочку без данных». Со спринтом 8 это перестало быть
правдой: на ней может висеть владение карточкой. Теперь владение **переносится** на учётку
персонала перед удалением — человек тот же самый. Заявки не переносим: на `market.claim`
висит `UNIQUE (entry_id, user_id)`, и перенос упал бы при совпадении; их подметает уборка.

Проверено в `npm run check:track` — 30 утверждений: все исключения, идемпотентность, отказ
на нулевом сроке, содержимое журнала (кого и на каком основании, и что имени с `sub` там
нет) и **три гонки** — вход, появление владения и подача заявки между выборкой и удалением.
Таблицы Payload подменяются теневой схемой через `search_path` (без `,public`: с ним провал
подмены был бы не виден), и отдельная строка проверяет, что подмена состоялась, — иначе
проверка удаляла бы настоящих людей из базы разработчика.

## Удаление по просьбе человека

Построено 2026-09-03 по решению владельца. `POST /api/account/delete`, форма на `/dannye` за
раскрывающимся блоком: два осознанных действия вместо диалога подтверждения — работает без
JavaScript и не зависит от того, перехватит ли браузер `confirm`.

Идёт через `eraseUser` — **ту же точку, что и регламент**: ссылки снимаются, строка уходит в
журнал уничтожения. Отличается только основание: `request` вместо `retention_12m`, и по нему
потом отличают «истёк срок» от «человек попросил».

Два отказа, оба со словами, а не молча:

- **персоналу** — учётка `superadmin` это доступ к админке и к записи поездок, её удаляют
  осознанно из админки, а не кнопкой на странице о данных;
- **владельцу карточки бизнеса** — удалив, мы бы молча сняли владельца с карточки вместе с
  кабинетом и работниками (`ON DELETE SET NULL`). Сначала персонал снимает владение.

Проверено сквозняком настоящей сессией Payload (временный роут, в репозиторий не вошёл):
посетитель удаляется, его заявки убраны, в журнале основание `request`; владельцу карточки
отказано, аккаунт и владение целы; без сессии — отказ.

### Три пути, одна реализация

Человек исчезает тремя путями, и все три ведут в `recordUserErasure` — единственную
реализацию уборки и записи в журнал:

| Путь | Как попадает | Основание в журнале |
|---|---|---|
| срок | регламент → `eraseUser` | `retention_12m` |
| просьба | `POST /api/account/delete` → `eraseUser` | `request` |
| админка | хук `afterDelete` коллекции `users` | `admin` |

Действие в журнале различает посетителя (`delete_visitor_account`) и сотрудника
(`delete_staff_account`): это разные события, и сводить их в одну строку значило бы потерять
смысл обоих.

⚠️ **Почему хук — подстраховка, а не главный путь.** `afterDelete` выполняется **до коммита**
транзакции Payload: если удаление после него откатится, мы уже сотрём заявки живого человека
и запишем в журнал, что его стёрли, — ровно тот дефект, который ревью нашло в первой версии
ретеншна. Поэтому `eraseUser` убирает **после** возврата из `delete`, когда коммит уже
состоялся, и помечает себя в `req.context`, чтобы хук промолчал и не завёл вторую строку.
Для админки такой точки нет, и выбор там между «редкая ложная строка» и «удаление из админки
не убирает за собой вовсе» — второе хуже.

Хук стоит под гейтом `accountRetentionReady` и не имеет права уронить удаление: до миграции
схем `market`/`track` нет, и попытка убрать за собой отняла бы у персонала возможность
удалить пользователя. В этом случае он молчит, а висячие ссылки подметает
`sweepOrphanUserRefs`.

Проверено сквозняком в живом Next (временный роут, в репозиторий не вошёл): удаление из
админки даёт ровно одну строку с основанием `admin` и убирает ссылки; у сотрудника своё
действие; путь через `eraseUser` даёт **одну** строку, а не две.

Правовые тексты (РКН, политика, форма согласия) — спринт 7, отложен владельцем.
