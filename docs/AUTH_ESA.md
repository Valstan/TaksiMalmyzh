# Вход через единый вход экосистемы (ЕСА, `вход.вмалмыже.рф`)

Построено 2026-09-02 по просьбе владельца «вход через ВК» (2026-08-29). Прямой интеграции с
ВК нет: единый вход экосистемы делает ЕСА, а ВК для неё — один из способов войти. Сайту
это невидимо и таким останется: ЕСА отдаёт только `sub`, `name` и по scope `email`
(решение владельца D-063, 2026-09-02). Пользователь ПОЗВОНИ = `sub`.

## Для кого

**Для персонала админки**, не для посетителей. Справочник анонимен: смотреть номера и
звонить можно без входа, и так должно остаться. Аккаунты посетителей — Фаза 2 и забор
M0.A §10 ([`PRIVACY_GEODATA_DESIGN.md`](PRIVACY_GEODATA_DESIGN.md)); этот вход его не
трогает — модератор не субъект справочника.

## Реквизиты клиента (прод, заведён 2026-09-01)

| Поле | Значение |
|---|---|
| issuer | `https://вход.вмалмыже.рф` (`https://xn--b1ae3a1a.xn--80adkdyec4j.xn--p1ai`) |
| `client_id` | `pozvoni` |
| тип | **public**, Authorization Code + PKCE S256, `token_endpoint_auth_method=none` |
| `redirect_uri` | ровно один: `https://позвони.вмалмыже.рф/api/auth/oidc/callback` (в punycode — так строит `lib/oidc.ts` из `lib/sites.ts`) |
| scopes | `openid profile` |
| discovery | `/.well-known/openid-configuration`; JWKS — по discovery (`/.well-known/jwks.json`), RS256 |
| logout | у ЕСА нет ни `end_session_endpoint`, ни back-channel; поддерживать нечего |

Секрета **не существует** — хранить и ротировать нечего. Всё, что нужно на боксе, —
`OIDC_CLIENT_ID=pozvoni` в env приложения; это выключатель, а не секрет.

## Как устроено

- `lib/oidc.ts` — конфигурация, discovery с кэшем, PKCE, обмен кода, проверка ID-токена
  (подпись по JWKS, issuer, audience, nonce). Личность берётся из проверенного
  ID-токена, не из `/userinfo`.
- `lib/oidc-flow.ts` — состояние одного прохода (`state`, `nonce`, `verifier`, режим) в
  httpOnly-куке `oidc-flow` с путём `/api/auth/oidc` и сроком 10 минут; одноразовая.
- `app/(app)/api/auth/oidc/start` — начало. Гость → режим `login`; вошедший (обычная
  сессия Payload) → режим `link`.
- `app/(app)/api/auth/oidc/callback` — возврат. В режиме `link` привязывает `sub` к
  учётке живой сессии; в режиме `login` ищет пользователя по `sub` и выдаёт сессию.
- `lib/oidc-session.ts` — выдаёт ту же сессию Payload, что и парольный login
  (`sessions` + JWT + кука `payload-token`). Для админки и гейта записи поездок
  (`lib/track-gate.ts`) такой вход неотличим от парольного.
- `collections/Users.ts` — поле `oidcSub`: уникальное, в админке только для чтения,
  через API не обновляется. Миграция `20260902_120000_oidc_sub`.
- Админка: ссылка под формой логина (`beforeLogin`) и карточка привязки на главной
  (`afterDashboard`). Оба компонента молчат, пока `OIDC_CLIENT_ID` не задан.

## Почему регистрации нет и не появится

Незнакомый `sub` не создаёт пользователя. Единственный способ появиться — **привязка**:
войти паролем и нажать «Привязать единый вход» на главной админки. Так «вошедший» на
этапе A остаётся ровно тем, кого завёл владелец, а закрытая снаружи коллекция `users`
не открывается через боковую дверь.

## Почему вход только на корневом домене

Redirect URI один, и он на `позвони.вмалмыже.рф`: иначе каждый новый поддомен матрёшки
становился бы заявкой на чужой стороне. Кука сессии Payload хостовая и на поддомены не
распространяется **намеренно**: кука на всю зону `.вмалмыже.рф` уезжала бы соседним
проектам той же зоны. Админка живёт на корне — этого достаточно.

## Что проверить на проде после первой выкатки с `OIDC_CLIENT_ID`

1. `GET /api/auth/oidc/start` → `302` на `…/oidc/authorize?client_id=pozvoni&…code_challenge_method=S256`.
2. Войти паролем → на главной админки карточка «Не привязан» → «Привязать» → ЕСА (пароль
   или ВК) → возврат в `/admin`, карточка «Привязан».
3. Выйти → под формой логина «Войти через единый вход» → ЕСА → `/admin` без пароля.
4. Незнакомый аккаунт ЕСА без привязки → текст «не привязан к ПОЗВОНИ», статус 403.

Смоук без браузера — четыре `curl` у Сарафана (`docs/ops/esa-smoke-without-browser.md`
в их репозитории, только чтение). Для него нужен тестовый аккаунт ЕСА: саморег с
инвайт-кодом из vault владельца. Заметьте: для публичного клиента шаг 3 их смоука идёт
без `-u`, с `client_id` и `code_verifier` в теле.
