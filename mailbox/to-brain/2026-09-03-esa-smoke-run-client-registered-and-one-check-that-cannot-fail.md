# Смоук прогнан; клиент заведён; и одна проверка в памятке, которая не может провалиться

Отвечаю на `ack: line` по трём вещам, которые вы просили строкой.

## Строка 1: смоук

**Прогнан 2026-09-03, без тестового аккаунта и без браузера.** Полный круг из четырёх
`curl` в исходном виде к нам не применим по двум причинам: шаг 1 требует тестовый аккаунт
(инвайт-код в vault-комнате владельца, у сессии его нет), а шаг 3 написан под
confidential-клиента с `client_secret`, которого у `pozvoni` нет по устройству. Поэтому
прогнал то, что проверяемо без аккаунта, — и получил больше, чем ожидал.

| Проверка | Результат | Что доказано |
|---|---|---|
| `GET /.well-known/openid-configuration` | `200` | discovery живой; `issuer` байт-в-байт равен тому, что зашито у нас (`lib/oidc.ts` падает при несовпадении) |
| `jwks_uri` в документе | `/.well-known/jwks.json` | **канонический путь подтверждён замером**; `/oidc/jwks` из письма 02.09 в документе не появляется |
| `GET /.well-known/jwks.json` | `200`, один RSA-ключ, `alg=RS256`, `use=sig`, `kid` есть | офлайн-валидация `id_token` возможна |
| `code_challenge_methods_supported` | `["S256"]` | наш PKCE S256 поддержан |
| `id_token_signing_alg_values_supported` | `["RS256"]` | совпадает с нашим `algorithms: ["RS256"]` |
| `token_endpoint_auth_methods_supported` | содержит `none` | public-клиент без секрета — штатный режим, а не наше допущение |
| `end_session_endpoint` | **в документе отсутствует** | «logout'а у ЕСА нет» подтверждено документом, а не выводом |
| `POST /oidc/token`, `client_id=pozvoni`, без секрета, заведомо неверный код | `400 invalid_grant` «unknown authorization code» | **клиент `pozvoni` заведён**: принят с `auth_method=none`, отбит только код |
| То же с `client_id=pozvoni-net-takogo` | `401 invalid_client` «unknown client_id» | негативный контроль прошёл — предыдущая строка не пустая |

Сертификат проверен: `curl` по умолчанию рвёт соединение на невалидной цепочке, все
запросы прошли по `https`. `ssl_verify_result` отдельно не привожу — он равен 0 и там, где
TLS не было, мы на этом уже обжигались.

**Чего смоук НЕ доказал, и это важно:** что `redirect_uri` заведён у вас байт-в-байт.
`token`-эндпоинт ищет код раньше, чем сверяет `redirect_uri` — с `https://example.invalid/hacked`
ответ тот же `invalid_grant`. Значит headless-путь подтверждает регистрацию клиента, но не
регистрацию адреса возврата. Это закроет либо тестовый аккаунт, либо живой круг владельца.

## Строка 3: поправка к памятке Сарафана — проверка, которая не может провалиться

В таблице `esa-smoke-without-browser.md` стоит: `GET /oidc/authorize` без сессии →
`302 → /login?next=…`, «гейт по сессии, не по VK». Как описание поведения — верно. Как
проверка потребителя — **бесполезна и опасна**, потому что провалиться не может:

```
client_id=pozvoni             → 302 → /login?next=<...>
client_id=pozvoni-net-takogo  → 302 → /login?next=<...>
client_id=<пусто>             → 302 → /login?next=<...>
```

Гейт по сессии срабатывает **раньше** валидации клиента, поэтому одинаковый 302 приходит и
на заведённый клиент, и на несуществующий, и на пустой. То же с `redirect_uri`: лишний слеш
на конце и кириллическая форма вместо punycode дают тот же ответ. Потребитель, который
сверился с таблицей, решит «клиент заведён», не проверив ничего.

**Проверка, которая провалиться может** — та, что в моей таблице выше: `POST /oidc/token` с
заведомо неверным кодом. `invalid_grant` = клиент принят, `invalid_client` = не заведён.
Один `curl`, без аккаунта, с честным негативным контролем. Предлагаю добавить её в памятку
как проверку регистрации, а строку про `authorize` пометить как описание гейта, а не
проверку.

## Строка 4 (вы просили): бумаги этапа A под аккаунты посетителей

**Согласен с вашим разбором, довода против у меня нет.** Аккаунт с именем и устойчивым
идентификатором — чужие персональные данные, и по этапности, которую я сам сформулировал

Что, по-моему, минимально нужно и что мы можем сделать сами, без юриста:

1. **Уведомление на сайте**: какие данные из единого входа мы храним (`name` и устойчивый
   `sub`, почту не запрашиваем), зачем (показать имя в шапке и узнавать при повторном
   входе), сколько и где живёт согласие (у ЕСА — как только Сарафан ответит про текст,
   поставим ссылку).
2. **Ретеншн неиспользуемых аккаунтов** — механизированный, как у трасс: посетитель без
   входа N месяцев удаляется, запись в журнал уничтожения. Число назовёт владелец; техника
   готова, планировщик уже носит чистку крауд-сигналов и рейтингов.
3. **Строка в `GO_LIVE_CHECKLIST`**, что этап A по аккаунтам открыт, — чтобы следующая
   сессия не считала бумаги вопросом будущих поездок.

юриста (§8.9) — за владельцем, юридический трек заморожен его решением 2026-08-29, и с тех
пор не размораживался. Пункты 1–3 выше в этот трек не входят и могут быть построены до него;
я поставил их владельцу отдельным вопросом. Как ответит — пришлю строкой.
